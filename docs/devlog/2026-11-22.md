# 2026-11-22: a task can use a second CNode (TODO 1.2)

Requested: continue the roadmap toward M20, build what is needed, fix what is broken.
This entry covers the first step taken in that run.

## What changed

- `kernel/src/cspace.rs`: `derive`, `move`, `delete` and `revoke` act on the CNode
  the invoked capability names (any CNode capability the task holds with the
  WRITE right), with slot numbers relative to it. `retype` puts its new
  capabilities in the CNode named by its third argument; 0 keeps the old
  meaning, the task's own space. Retyped CNodes are 1 to 128 slots. Destroying a
  CNode now deletes every capability inside it (`State::destroy_contents`), run
  from inside the delete that destroyed it.
- Two rules keep that recursion shallow: a capability to a CNode never leaves its
  task (unchanged), and a CNode capability may only be stored in the task's own
  space, so a second CNode never holds one.
- `user/src/bin/capdemo.rs`: steps 53 to 72. Step 55 used to expect `WrongKind`
  for `move` on a retyped CNode; it now expects `EmptySlot` because the call is
  allowed.
- Docs: `TODO.md` (1.2 done, new 1.2b for moving between two CNodes),
  design doc section 10 CNode row, `ARCHITECTURE.md`, `CHANGELOG.md`.

## A mistake found on the way

A first version looked up slot 0 for the destination CNode when the third
argument was 0. The random-arguments self-test moved slot 0 away and retype then
never succeeded (`operation 1 succeeded only 0 times`). 0 now means "own space"
without any lookup, which is what it meant before.

## Not shown

A capability stored in a second CNode cannot be used from there (1.2b). Destroying
a task whose second CNode is still full is covered only through the untyped
revoke path of teardown, not by a separate test.

## Later the same day: moving between CNodes (TODO 1.2b)

Decision: one new operation, `move_from` (invoke label 10), invoked on the
destination CNode, taking the source CNode's slot, the slot to take and the slot to
fill. It moves (does not copy), so the derivation order is untouched. A capability
to a CNode may only move into the task's own space, which keeps the rule that a
second CNode never holds a CNode capability. Copy between CNodes was left out: no
task needs it yet.

Observed (debug, software emulation): `selftest: all 113 tests passed`,
`boot test: PASS (6 variants)`; capdemo steps 73 to 83 pass. Negative control:
with the CNode guard disabled, `capabilities_work_from_ring_3` failed with
`left: Exited(82)`; code restored from a saved copy.
