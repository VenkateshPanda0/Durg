### Spec findings that changed the design
- Base revision 3 makes the HHDM restrictive. Only usable, bootloader-reclaimable, kernel/modules and framebuffer regions are mapped. **ACPI tables are not**, so the RSDP address (physical) must not be dereferenced through the HHDM. M2 records the address only. M3 maps it itself.
- Memory map guarantees (sorted by base; usable and bootloader-reclaimable entries 4 KiB aligned and non-overlapping) are now checked by self-tests.

## M3 (part 1): CPU structures, exceptions, PIC, ACPI

### Done

## M4: physical memory manager

### Done
- `durg-pmm` crate (`#![forbid(unsafe_code)]`): bitmap frame allocator with two bitmaps (managed and free) giving three states (not ours, free, allocated). `free` refuses frames out of range, never owned, or already free. `check_invariants` verifies five invariants.
- Host tests: 12 unit tests plus a model-based property test (512 cases, up to 300 operations each) against a `BTreeSet` reference model. `proptest` is a dev-dependency only.
- `mm::frame`: builds the pool from the Limine memory map (usable RAM above 1 MiB only), puts the bitmaps in the first usable region that fits, covers frames only up to the highest usable address (15 KiB instead of 32 MiB), re-entrancy guard, `alloc_frame`, `alloc_zeroed_frame`, `free_frame`.
- Boot now prints `PMM: 52835 frames (206 MiB) managed ...` and runs an allocate/free round trip.
- `mm::paging` now takes page-table frames from the allocator. The four-page boot pool from M3 is removed.
- `lapic::init` verifies its mapping by walking the page tables back (this also gives `translate` a runtime use).
- 7 new self-tests (32 total): totals vs an independent calculation, usable/distinct/aligned/outside-bitmaps, double free and foreign frames, zeroed frames are zero, 20,000-operation stress with unique per-frame patterns, exhaustion and recovery, page-table frames come from the allocator.

### Verified (real output)
- `cargo xtask test` and `--release`: `boot test: PASS (4 variants)`, `selftest: all 32 tests passed`.
- `PMM: 52835 frames (206 MiB) managed, 52835 free; bitmaps 15 KiB at physical 0x100000` (debug build), `PMM: allocate/free round trip ok`.
- Host: `cargo test -p durg-acpi -p durg-paging -p durg-pmm`: 17, 11 and 13 passed.
- `cargo fmt --check` and `cargo clippy -D warnings` clean for all four kernel feature sets, xtask and all three pure crates.
- **Mutation tests on the crate (4 mutants, all caught):** alloc not clearing the free bit (7 of 13 tests failed), accepting a double free (2), accepting a never-owned frame (3), `add_range` off by one (2). Original restored byte for byte.
- **Fault injection in the kernel (2, both caught):** no zeroing in `alloc_zeroed_frame` failed `pmm_zeroed_frames_are_zero` (`frame 0x200000 was not zeroed at offset 0x0`). An allocator that did not mark frames used was caught first by an unrelated test (`lapic_is_mapped_uncached_at_its_physical_base`), because the same frame went to the page-table code twice and corrupted the APIC mapping.
- Unsafe: 34 blocks in about 3,400 kernel lines (including test code): x86_64/mod 12, frame 7, trap 4, limine 3, gdt 2, lapic 2, paging 2, acpi 1, idt 1. The three pure crates contain none.

### Decisions made this session (small, reversible, for the owner to see)
- Only usable RAM above 1 MiB is in the pool. Bootloader-reclaimable memory (42.6 MiB on QEMU) is left out until M5. The first MiB is kept out as a policy.
- The allocator tracks "managed" separately from "free", so a free of a frame that was never ours is an error instead of a silent addition to the pool.

### Mistakes
- My first property test built its operation list through a nested deterministic runner, which defeats proptest's shrinking and random generation. Rewrote it with `prop_flat_map`.
- Several edits failed to apply because `rustfmt` had reflowed the text my scripts searched for. Caught by assertions in the scripts, not silently.

### Not verified
- CI for M4 has not run.
- Performance. The search is a linear scan from a moving hint. The exhaustion test passes in QEMU, but no timing was measured.
- Behaviour under KVM, on real hardware, and with other memory sizes or layouts (every run used QEMU `-m 256M`).
- Anything multi-CPU: there is no lock.
- That the bootloader's memory map is right. The allocator trusts it.

## M5: the kernel owns its address space

### Done
- `limine::capture`: the memory map, HHDM offset and RSDP address are copied into kernel memory at the start of boot and every accessor reads the copy. Nothing reads bootloader memory afterwards.
- `mm::paging` rewritten around `AddressSpace`: translate, `map_page`, `map_2m`, `map_range` (2 MiB pages where aligned), `unmap` (refuses to split a huge page, invalidates the TLB), `activate`. Any root works, not only the active one. `hhdm_reachable` reflects whichever tables are active.
- `mm::vm::take_over`: builds the kernel's own address space (image sections mapped with W^X from linker-script boundaries, direct map limited to RAM, bootloader memory and read-only ACPI), verifies it against the live tables, then loads CR3. The kernel image is not in the direct map, and neither are the framebuffer or reserved ranges.
- Kernel stack: 16 pages in PML4 slot 508 with an unmapped guard page below. Boot is now two stages, switching stacks between them.
- Double fault handler recognises a guard-page hit (CR2 or RSP in the guard page).
- `frame::reclaim_bootloader_memory`: adds the bootloader-reclaimable memory above 1 MiB to the pool, and refuses to run before the kernel is on its own page tables.
- New variant `stack-overflow` (feature `so-test`): real recursion into the guard page.
- Boot-time map/write/read/unmap round trip; `lapic::init` verifies its mapping.
- 13 new self-tests (45 total) and one more boot variant (5 total).
- ADR-0007 records the policy.

### Verified (real output)
- First boot with the new tables: `VM: kernel page tables active (root 0x104000, 17 table frames)`, `VM: kernel stack 0xfffffe0000001000..0xfffffe0000011000 (64 KiB), guard page ... unmapped`, `PMM: reclaimed 10967 frames (42 MiB) of bootloader memory`, `VM: map/write/read/unmap round trip ok`, LAPIC mapped in the new tables, 5 timer ticks.
- `cargo xtask test` and `--release`: `boot test: PASS (5 variants)`, `selftest: all 45 tests passed`.
- Stack overflow: `kernel stack overflow detected: CR2 0xfffffe0000000e58, RSP 0xfffffe0000000e60, guard page 0xfffffe0000000000..0xfffffe0000001000` then `double fault handled on the IST stack`, exit 33.
- Host: `cargo test -p durg-acpi -p durg-paging -p durg-pmm`: 17, 11, 13 passed.
- fmt and clippy `-D warnings` clean for all five kernel feature sets, xtask and the three pure crates.
- **Negative controls (all caught):** text mapped writable (`page ... in text is writable and executable`); guard page and full stack mapped (`the guard page is mapped`, and the stack-overflow variant failed because the overflow was no longer attributed to the guard page); `invlpg` removed from `unmap` (`paging_unmap_takes_effect_despite_the_tlb` failed, so a stale TLB entry survived). Files restored and compared byte for byte.
- Unsafe: 44 blocks in about 4,900 kernel lines (including tests): x86_64/mod 13, frame 7, trap 6, limine 5, paging 3, vm 3, gdt 2, lapic 2, acpi 1, idt 1, main 1. The pure crates contain none.

- I left a nonsensical `assert_eq!(... .or_else(...))` in `paging_unmap_errors`. A clear assertion right below it covered the case. I removed it.
- Several scripted edits failed to apply because `rustfmt` had reflowed the text, and one script had a syntax error. The assertions in the scripts caught each one, nothing was half-applied.
