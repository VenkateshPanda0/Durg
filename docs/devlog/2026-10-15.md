## M2: serial console and boot information

### Done
- Limine bindings extended: memory map, HHDM and RSDP requests, plus request start/end markers. IDs and layouts were checked against the protocol document and the pinned `limine.h`, not written from memory.
- A real 16550 UART driver for COM1 (baud divisor, 8N1, FIFOs, loopback self-test).
- `print!`, `println!`, `info!`, `warn!`, `error!`. Panic output now includes location and message.
- `boot::print_boot_info`: memory map table, usable RAM total, HHDM offset, RSDP physical address.
- In-kernel test registry (stable Rust, no custom test framework): `selftest` runs 7 tests, `fail-demo` adds one that always fails.
- `cargo xtask test` now boots three variants and judges each: plain boot, selftest, and fail-demo (which must exit 35).

### Verified (real output)
- Plain boot prints the memory map (31 entries, 207 MiB usable under QEMU `-m 256M`), HHDM offset `0xffff800000000000`, RSDP physical `0x000000000f77e014`, exit status 33.
- `selftest`: `selftest: all 7 tests passed`, exit status 33.
- `fail-demo`: `test deliberate_failure ... PANIC: panicked at kernel/src/selftest.rs:177:5: this failure is deliberate`, exit status 35, and the harness counts that variant as a pass.
- `cargo xtask test` and `cargo xtask test --release`: `boot test: PASS (3 variants)`.
- `cargo fmt --check` clean. `cargo clippy -D warnings` clean for default, `selftest` and `fail-demo` features.
- Unsafe: 6 blocks (3 in `arch/x86_64.rs`, 3 in `limine.rs`), in a kernel of about 800 lines including tests.

### Spec findings that changed the design
- Base revision 3 makes the HHDM restrictive. Only usable, bootloader-reclaimable, kernel/modules and framebuffer regions are mapped. **ACPI tables are not**, so the RSDP address (physical) must not be dereferenced through the HHDM. M2 records the address only. M3 maps it itself.
- Memory map guarantees (sorted by base; usable and bootloader-reclaimable entries 4 KiB aligned and non-overlapping) are now checked by self-tests.

### Not verified
- CI for M2 has not run yet.
- Behaviour under KVM, and on real hardware (out of scope by design).
- The 16550 driver beyond what QEMU emulates. The loopback test passed here, which shows the programming sequence works on QEMU's model of the chip, not that it is correct on every UART.
- Serial output is unlocked. That is safe only while there is one CPU, no interrupts and no threads (M7 must fix this).
