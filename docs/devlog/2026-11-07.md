# 2026-11-07: Reject spawner creation by retype

The pure capability core accepted `Kind::Spawner` in `retype`, although a spawner
is authority issued at boot rather than an object backed by untyped memory. The
kernel's `retype` dispatch already restricts accepted kinds, so this was not a
known route for a guest task to mint the authority. Keeping the core permissive
would nevertheless make that protection depend on every caller repeating the rule.

The core now rejects spawner retype with `BadSize` before modifying slots or the
untyped watermark. A regression test first failed against the previous code, then
passed after the check; the capability-operation fuzzer also asserts the rule.
This is defense in depth, not proof that spawner authority cannot be forged by
other paths. The interim spawner still allocates on behalf of tasks (ADR-0011).

## Checker range boundaries

`check_invariants_in` is documented to reject links outside its selected slot
range. Its internal lookup previously accepted any index the backing store could
read, so a truncated range containing an untyped region could incorrectly pass
while its child was outside the range. A regression test reproduced this before
the fix; the checker now restricts lookups to the requested range and tests both
ends and arithmetic overflow. The kernel self-test already uses a bounded copy;
this change fixes the shared checker contract rather than a demonstrated guest
capability escape. Cross-space graphs need a different checker or a snapshot that
contains the entire graph.

## Untyped physical-range validation (2026-11-08)

Untyped regions must be aligned, sized within the supported range, and have a
representable end address. Previously `install_root` accepted malformed ranges,
and `retype` could use a corrupted region without checking those assumptions.
The kernel normally supplies allocator-reserved regions; no guest-reachable exploit
was established. The shared validator now rejects malformed ranges before writing
slots and the invariant checker validates sizes before shifting. Regression tests
failed against the previous behavior and now pass; the full host/Clippy matrix and
all six debug and six release QEMU variants passed locally, along with a 30-second
capability fuzz smoke run. This is hardening, not a security proof.

## Blocked user-task cancellation (M10, 2026-11-08)

The internal `JoinHandle::kill` now wakes a blocked user task, marks its wait
aborted and leaves it to exit at the syscall boundary. A waiting receiver, a
caller waiting for a receiver, and a caller waiting for an accepted reply are
exercised from ring 3. The tests check killed status, stale reply rejection and
resource reclamation. Running kernel work is not interrupted; this is not a
user-facing task-control capability, and notification waits do not exist yet.

The 109 kernel self-tests passed in debug and release, along with all six boot
variants in each profile, host tests and Clippy. As a negative control, removing
the wake caused the receiver-wakeup assertion to fail in QEMU; the source was
then restored. This does not prove SMP safety: the scheduler is single-CPU.

## Atomic reserved-block return (M10/M11 prerequisite, 2026-11-08)

The PMM's general `add_range` is deliberately additive, so using it to release a
reserved block could add part of a mixed range before reporting a failed return.
The new exclusive operation checks the whole range before mutation. The kernel
also rejects block releases with invalid size or physical alignment before
accessing the allocator. It still relies on the caller's ownership records; the
bitmap cannot prove who owns an unmanaged frame. This is not a DMA-capability or
IOMMU implementation.

A host regression test and randomized per-frame model verify atomic refusal and
accounting. A QEMU test covers partial overlap, double release, bad alignment
and oversized shifts. Removing the preflight made the host regression fail, and
was then reverted. All host checks and the six debug and six release QEMU variants
passed locally; the self-test variants reported 110 passing kernel tests.

## Split virtqueue layout groundwork (M11, 2026-11-08)

Added a pure, allocation-free, no-unsafe `durg-virtio` split-queue layout
validator using the Virtio 1.2 section 2.7 sizes and alignments. It rejects queue
sizes outside the device/spec limits, misalignment, address overflow and region
overlap. Boundary and exhaustive small-address tests pass; mutations for size,
alignment, ring length and overlap were all caught. Host Clippy and bare-metal
`no_std` compilation passed. It is not a driver, DMA ownership check, queue
implementation, transport, notification or memory barrier. Full M11 remains open.
